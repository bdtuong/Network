# Challenges and solutions

The assignment combines a UDP streaming objective with a TCP file-transfer example. Following the explicit UDP file-transfer milestone resolves that conflict: TCP provides admission and session lifecycle, while UDP carries every distributed message and file record. The browser cannot use raw UDP, so a loopback HTTP bridge owns a real socket client. This preserves the network learning objectives while satisfying the HTTP/JavaScript UI milestone.

UDP reliability requires more than resending entire files. Each encrypted datagram has a unique counter, selective ACK, bounded in-flight window and retry deadline. A delayed or lost chunk therefore causes retransmission of that packet only. Out-of-order chunks write directly to their indexed disk positions. Completion may arrive early, so the receiver remembers completion until its unique-byte count reaches the advertised size. SHA-256 then decides whether the temporary file may be finalized. A test sends intentionally incorrect metadata hashes and verifies that no successful file survives.

Reliable hop delivery does not itself protect relay buffers from a fast sender and slow receiver. An additional receiver-credit window restricts each file to sixteen unacknowledged chunks. This limits queued relay work without loading files into memory. It also leaves chat records free to proceed without waiting for a missing file chunk. Shared congestion windows and dispatch workers still introduce scheduling contention; the implementation makes no claim of unlimited stream isolation or guaranteed chat order.

Encryption adds a subtle nonce invariant. Both directions could otherwise generate the same counter under the same key. Distinct client-to-server and server-to-client keys solve that issue, while retransmission reuses the original complete ciphertext rather than encrypting different data under the same nonce. Header authentication binds ciphertext to the session, packet kind and counter. An 8192-counter deduplication window prevents packet replay from creating duplicate chat/file events. The unauthenticated X25519 exchange protects against passive sniffing but not active impersonation, a deliberate trusted-LAN limitation.

Threaded cleanup was an actual integration finding: a transport could enter its send tick after another thread closed the socket. Shutdown now changes state under the transport lock and the reactor checks it before sending again. Warnings-as-errors also identified unclosed read handles in tests, which were replaced by managed path reads. These checks matter because a superficially successful file transfer can conceal background-thread failures and resource leaks.

The test impairment adapter lives only under tests. Deterministic loss, duplication, reordering and latency exercise real UDP sockets rather than fake application callbacks. The large-file test runs concurrently with chat, and the concurrency test establishes twenty sessions before simultaneous broadcasts. These demonstrate the intended educational workload; they do not establish production Internet scalability, fairness, hostile-client resistance, or automatic reconnection.
